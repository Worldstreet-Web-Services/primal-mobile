## Frontend boundary now enforced

Primal calls the API Gateway for product operations. It does not call LinkPay
or Dextopus directly. The current frontend exposes only capabilities supported
by the public Gateway contract:

| Capability | Public Gateway support | Frontend state |
| --- | --- | --- |
| SIWE challenge, verify, refresh, logout and identity | Yes | Enabled |
| Subscription checkout, payment polling and cancellation | Yes | Enabled |
| LinkPay account provisioning and account read | Yes | Enabled |
| LinkPay bank account funding and deposit history | Yes | Enabled |
| Bank list, account validation, withdrawal quote and payout | Yes | Enabled |
| LinkPay airtime/data/bill purchase and transaction polling | Yes | Enabled |
| General crypto deposit | No | Disabled and labelled as backend-required |
| General crypto withdrawal | No | Disabled and labelled as backend-required |
| Fiat-to-crypto or crypto-to-fiat conversion | No | Disabled |
| Cross-chain routing or sponsored gas | No | Disabled |
| ARK and WorldStreet product operations | No | Not exposed as working Gateway rails |
| Aggregated Pulse/activity feed | No | Existing concept screen is not backend-backed |

Development LinkPay fixtures and the client-side paywall bypass are off in the
current local environment. Live financial testing therefore requires a real
Primal session and active backend entitlement.

## P0 — make the deployed OpenAPI authoritative

The supplied frontend integration context says that the deployed OpenAPI wins
when syntax differs. The deployed API v0.1.0 currently conflicts with that
context in ways that prevent reliable generated clients and contract tests:

1. `x-correlation-id` is marked required on many operations, while the written
   context says it is optional and generated by the Gateway when absent.
2. `ProvisionAccountDto` has no properties, while the written contract requires
   `idempotencyKey`, name, phone, email, BVN, country and currency.
3. `ValidateBankDto` has no properties, while the written contract requires
   account number, bank UUID, country and currency.
4. `WithdrawalDto` documents only `amount`; it omits the idempotency key,
   destination account, destination bank UUID and narration.
5. `PurchaseServiceDto` documents only `amount`; it omits the remaining service
   purchase fields and idempotency key.
6. `CancelSubscriptionDto.atPeriodEnd` is emitted as `type: object`, not a
   boolean.
7. Several LinkPay list operations omit the documented pagination and status
   query parameters.
8. Most successful response schemas are empty, so account, balance, deposit,
   withdrawal, subscription, payment and service transaction payloads cannot
   be validated from OpenAPI.

Backend action: correct the controller/DTO decorators, publish the complete
response schemas, redeploy, and commit a generated OpenAPI snapshot for CI.

## P0 — prove the currently supported financial rails

The integration context still lists production provider credentials, chain and
token allowlists, treasury configuration, and sanctioned end-to-end settlement
as incomplete. Before customer funds are enabled, provide a staging principal
with an active entitlement and prove:

- LinkPay account provisioning through all intermediate and terminal states;
- a real/sandbox bank transfer progressing `DETECTED` → `CREDITED`;
- bank validation returning the account name shown before confirmation;
- withdrawal quote totals matching provider debits;
- withdrawal progression through settlement, failure and reversal;
- ambiguous mutation timeout recovery using the same idempotency key;
- subscription transfer settlement followed by entitlement propagation;
- correlation IDs on errors and ownership-safe 404 responses.

Frontend fixtures are useful for interface development but are not acceptance
evidence for any item above.

## P1 — general crypto deposit contract

No public route currently lets Primal obtain a user deposit address. Dextopus
credentials and static-address lifecycle must remain behind the Gateway.

The backend contract needs to define, with final route names in OpenAPI:

- the allowlisted origin networks and assets;
- whether an address is reusable or checkout-specific;
- idempotent address creation/retrieval for the authenticated user;
- deposit address, exact asset, network, minimum, expiry and refund rules;
- settlement network, asset and authenticated-user destination;
- deposit status/history with terminal failure/refund states;
- provider references safe for support, without provider credentials.

The frontend will not restore the crypto deposit control until these operations
exist in the deployed OpenAPI and have passed sanctioned settlement tests.

## P1 — crypto withdrawal contract

No public route currently owns a managed crypto withdrawal. Define:

- supported source networks/assets and destination validation rules;
- a quote containing the exact amount, provider/network fees, total debit,
  expiry, gas responsibility and any route minimum;
- an idempotent initiation operation bound to the authenticated wallet/user;
- step-up authorization requirements when implemented;
- status lookup/history covering submitted, processing, settled, failed,
  refunded/reversed and expired outcomes;
- transaction hash/reference only after broadcast, never as proof of settlement;
- explicit Solana support or an explicit unsupported response.

If withdrawals are intended to remain purely self-custodial wallet
transactions, document that as a separate supported product boundary, including
RPC ownership, gas estimation, token approvals, chain switching and support
responsibility. Do not leave the frontend to infer it from Decane capabilities.

## P1 — fiat/crypto conversion contract

No public route quotes or settles movement between the LinkPay NGN ledger and
the self-custody crypto wallet. A complete contract needs:

- supported direction, currency, chain and asset pairs;
- source amount, fees, rate, destination amount and quote expiry;
- an idempotent execution operation;
- source-balance reservation/debit rules;
- destination settlement and refund/reversal rules;
- status/history and reconciliation identifiers;
- compliance limits and any additional confirmation requirements.

Until all of those are backend-owned, Primal keeps fiat and crypto balances
separate and does not imply automatic conversion.

## Backend completion signal

A missing capability is ready for frontend integration only when:

1. its public operations and complete schemas are deployed in OpenAPI;
2. authentication, entitlement and ownership behavior are documented;
3. idempotency and ambiguous-timeout recovery are defined;
4. provider credentials remain server-side;
5. staging settlement has passed with correlation IDs retained;
6. the backend supplies test fixtures or a sanctioned test principal for CI/E2E.
